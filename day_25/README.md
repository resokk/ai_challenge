# День 25: мини-чат с RAG, источниками и памятью задачи

`python -m codeindex chat` — чат в терминале о коде из индекса. Он:

- **хранит историю диалога** (SQLite, `index/chat.db`; сессию можно продолжить после перезапуска, `--session`);
- **на каждое сообщение заново ищет контекст** через RAG дней 23–24;
- **отвечает с учётом найденного** — утверждениями с дословными цитатами, как в дне 24;
- **всегда выводит источники**: файл, строки, раздел и `chunk_id`. Если ничего не прошло порог релевантности,
  ответ — «не знаю, уточните», и показываются ближайшие найденные места.

### Память задачи

Кроме истории чат ведёт память задачи — короткую записку о разговоре:

| поле | что хранит | пример |
|---|---|---|
| цель | чего пользователь добивается в этом разговоре | «API интернет-магазина со списком заказов постранично» |
| уточнено | факты, которые пользователь сообщил о своей ситуации | «база PostgreSQL», «модели Order и Customer» |
| ограничения | требования и рамки | «никакого сырого SQL» |
| термины | договорённости о словах | «активный заказ: статус не cancelled» |

Как устроен один ход — три вызова модели 7B:

```
сообщение ──► 1. память задачи: обновить цель / уточнения / ограничения / термины
          ──► код: цель не меняется без явной смены (goal_changed), записанное не удаляется
          ──► 2. поисковый запрос в терминах библиотеки, ссылки разрешены по истории
                 («а как подтянуть покупателя?» → «select related model in the same query join»)
          ──► поиск (порог 0.62 + LLM-реранкер), имя самой библиотеки из запроса убирается
          ──► сообщение без вопроса (уточнение, ограничение, термин)? ──► «Записал в память задачи: …»
                                                                         + найденный по теме код
          ──► 3. ответ на вопрос в терминах библиотеки, на языке пользователя, утверждениями с цитатами
          ──► проверка цитат кодом ──► ответ + источники (или «не знаю» + ближайшие найденные места)
```

Инварианты держит код, а не модель:

- **цель** меняется, только если пользователь явно её сменил: побочный вопрос о погоде её не сбивает;
- **память только растёт**: модель может добавить пункт, но не удалить;
- **сообщение без «?», которое что-то добавило в память,** считается уточнением, а не вопросом;
- **прошлые «не знаю»** показываются модели как «(ответ не найден)», а не полным текстом,
  чтобы она их не повторяла.

Почему так, а не одним вызовом (каждое решение — исправление того, что сломалось на сценариях):

| что ломалось | причина | решение |
|---|---|---|
| на «список заказов» поиск находил `order_by` | в запросе оставались слова пользователя («orders»), а в коде `order` — это сортировка | отдельный вызов только для запроса, с примерами перевода в термины библиотеки |
| в запросе «ORMAR pagination» находился код конфигурации | имя библиотеки есть только в конфиге и импортах | код убирает имя проиндексированного пакета из запроса |
| после первого «не знаю» все ответы были «не знаю» | модель повторяла свой прошлый отказ из истории | в историю отказ попадает пометкой, без текста |
| «как получить заказы покупателя?» → «не знаю», хотя `filter` найден | модель искала в коде «заказы» и «покупателя» | отвечающая модель получает вопрос в терминах библиотеки и не видит историю |
| «база у нас PostgreSQL» → «не знаю, уточните» | модель считала уточнение вопросом | такие сообщения распознаёт код и отвечает «записал в память» |

Команды в чате: `/state` — память задачи, `/history` — история, `/new` — начать заново, `/quit` — выход.

```sh
python -m codeindex chat                       # сессия default
python -m codeindex chat --session orders      # отдельный разговор
python -m codeindex chat-eval eval/scenarios.json
```

### Проверка на длинных сценариях

`eval/scenarios.json` — два сценария по 13 сообщений:

- **orders-api** (по-русски): API заказов с пагинацией; по ходу пользователь уточняет базу и модели, ставит
  ограничение «без сырого SQL», вводит термин «активный заказ», задаёт посторонний вопрос о погоде и возвращается.
- **profile-import** (по-английски): ночной импорт профилей с шифрованием email; уточнение «Fernet, не хеш»,
  ограничение «без дублей», термин «stale profile», посторонний вопрос про Slack.

На каждом ходе проверяется:

- **показаны ли источники** (или ближайшие найденные, если ответ «не знаю»);
- **сохранилась ли цель** — по ключевым словам сценария в поле цели;
- **сохранилась ли память** — всё, что пользователь уточнил к этому ходу, по ключевым словам;
- **правильный ли источник** — на ходах, где известно, какой код должен найтись.

Полный прогон двух сценариев (26 сообщений, около 25 минут на локальных моделях):

|---|---|---|---|---|---|---|
| orders-api (рус.) | 9/13 | 4/13 | **13/13** | **13/13** | **12/12** | 7/8 |
| profile-import (англ.) | 5/13 | 4/13 | **13/13** | **13/13** | **12/12** | 4/8 |

«Записано в память» — сообщения без вопроса («база у нас PostgreSQL», «без дублей», термины): на них чат
отвечает, что внёс в память задачи, и показывает найденный по теме код.

Что видно:

- **Цель не теряется ни на одном из 26 ходов,** в том числе после посторонних вопросов о погоде и Slack и
  после возврата к теме («Вернёмся к API…» → правильный ответ `NoMatch`).
- **Все уточнения, ограничения и термины сохранены до конца разговора** (24/24 проверки).
- **Источники выводятся на каждом ходу:** у ответа — куски кода, из которых взяты цитаты; у «не знаю» —
  ближайшие найденные места; у уточнения — код по теме.
- **Ссылки на прошлые сообщения разрешаются:** «А как сразу подтянуть данные покупателя?» →
  `select_related`, «Отсортируй их…» → `order_by` с минусом, «Как исключить неактивные заказы?» (термин
  из памяти) → `exclude`.
- **В этом прогоне вопросы о погоде и Slack были приняты за уточнения** («Принял…»). Исправлено (вопросительный
  знак теперь всегда означает вопрос) и перепроверено отдельно: оба вопроса дают «не знаю», цель сохраняется.

Слабые места — полнота ответов во втором сценарии:

- «How does column encryption work?» — модель дописала к запросу «model field», и поиск ушёл в общий код колонок;
  ответ дан, но не про шифрование.
- «What does the hash backend do differently?» — `HashBackend` есть среди ближайших найденных, но не прошёл
  порог и реранкер, поэтому «не знаю».
- «How do I delete the stale ones?» — «не знаю»: ссылка «the stale ones» разрешена, но удаление не нашлось.
- «Can I run my own code after each profile is saved?» — сигналы `post_save` поиск не находит, как и в днях 23–24.
- Итоговые «подведи итог» отвечаются частично (первый сценарий) или «не знаю» (второй): вопрос охватывает
  весь разговор, а поиск достаёт 5 кусков под один запрос.

Ещё одно наблюдение: во втором сценарии цель записалась узко, по первому сообщению («понять, как работает
шифрование колонки… в ночном импорте профилей»), и дальше, как и положено, не менялась. Импорт в ней есть,
поэтому проверка проходит, но цель уже, чем весь разговор.

Все промахи в полноте ответов — на этапе поиска; удержание цели и памяти, разрешение ссылок и обязательные
источники работают.

# Ответы с цитатами (день 24)

Поверх поиска из дня 23 добавлен ответ на вопрос (`ask`). Каждый ответ обязан содержать:

- **ответ**;
- **источники** — файл, строки, раздел (qualified name) и `chunk_id` каждого куска кода, на который он опирается;
- **цитаты** — дословные фрагменты этих кусков.

```
вопрос ──► поиск дня 23 (rewrite + порог 0.62 + LLM-реранкер) ──► нет кусков выше порога? ──► «Не знаю, уточните…»
                                                                         │ есть
                                                                         ▼
          модель 7B отвечает в JSON: {known, statements: [{text, source, quote}], missing}
                                                                         │
          проверка кодом: цитата каждого утверждения дословно есть в куске? нет ──► утверждение вырезается
                                                                         │
          не осталось ни одного утверждения или known=false ──► «Не знаю, уточните…»
```

### Правила анти-галлюцинаций

1. **Порог релевантности.** Если после порога 0.62 и LLM-реранкера (оценка ≥ 5 из 10) не осталось ни одного
   куска, модель вообще не вызывается: ассистент отвечает «Не знаю», просит уточнить вопрос и показывает
   ближайшие найденные места с их скором, чтобы было от чего оттолкнуться.
2. **Ответ — это список утверждений, у каждого своя цитата.** Модель не пишет свободный текст: каждое
   утверждение идёт с номером источника и цитатой, которая его доказывает.
3. **Цитаты проверяются кодом.** Цитата засчитывается, только если она дословно встречается в куске
   (пробелы и переносы строк не важны, точка в конце тоже); короче 12 символов не засчитывается. Цитата,
   приписанная не тому источнику, перепривязывается к правильному.
4. **Утверждение без подтверждённой цитаты вырезается из ответа** и показывается отдельно как удалённое.
   Поэтому в ответ не попадает утверждение без дословного доказательства из кода. Пересказать свою цитату
   неверно модель всё ещё может — это и проверяет LLM-судья.
5. **Источники берутся из цитат,** а не со слов модели: файл, строки, раздел и `chunk_id` тех кусков,
   из которых есть подтверждённые цитаты.
6. **Не осталось ни одного утверждения — нет ответа.** Ответ превращается в «Не знаю».
7. **Модель может сама сказать «не знаю»** (`known: false`); ответ тогда тоже начинается с «Не знаю», а дальше
   идёт её объяснение, чего не хватает.
8. **Выдуманные имена.** Имена из `кода` в ответе, которых нет ни в одном источнике (например `MyModel.objects`),
   выводятся как предупреждение.

### Проверка на вопросах

`eval/answers.json`: 10 вопросов, ответ на которые есть в коде (8 на английском, 2 на русском),
и 3 вопроса без ответа (погода, pandas, MongoDB). Для каждого ответа проверяется:

- есть ли источники и цитаты;
- не пришлось ли вырезать утверждения с выдуманными цитатами;
- нет ли в ответе выдуманных имён;
- совпадает ли смысл ответа с цитатами — это решает LLM-судья (та же 7B), который видит только вопрос и пары
  «утверждение — цитата»;
- есть ли среди источников правильный кусок кода;
- на вопросы без ответа — сказал ли ассистент «не знаю».

### Результаты

| проверка | итог |
|---|---|
| ответ дан | 9/10 |
| есть источники (файл, строки, раздел, chunk_id) | 9/9 данных ответов |
| есть цитаты | 9/9 данных ответов |
| правильный кусок кода среди источников | 9/9 |
| без выдуманных имён в `коде` | 9/10 |
| ничего не пришлось вырезать | 8/10 (в одном ответе вырезано утверждение с неточной цитатой) |
| смысл совпадает с цитатами — LLM-судья 7B | 5/10 |
| смысл совпадает с цитатами — ручная проверка | 9/9 |
| «не знаю» на вопросах без ответа | 3/3 |

Что видно:

- **Источники и цитаты есть в каждом ответе.** Это следует из устройства: без подтверждённой цитаты
  утверждение не попадает в ответ, а без утверждений ответ становится «не знаю».
- **Режим «не знаю» сработал на всех трёх вопросах без ответа.** Погода и pandas отсеяны порогом без вызова
  модели (0–1 с), MongoDB прошёл порог, но модель сама ответила `known: false` и объяснила, чего не хватает.
- **Один ложный «не знаю»:** на «sort results in descending order» модель решила, что источники не отвечают,
  хотя в докстринге `QuerySet.order_by` написано про дефис перед именем поля. Строгий формат делает модель осторожнее.
- **LLM-судья 7B ненадёжен.** Все 4 ответа, которые он отклонил, подтверждаются цитатами при ручной проверке:
  например, утверждение «метод `delete` устанавливает статус сохранения в `False`» с цитатой
  `Sets model save status to False.` он счёл неподтверждённым. Автоматическую проверку смысла лучше делать
  моделью сильнее отвечающей.

Как к этому пришли (те же 13 вопросов):

| версия | без выдуманных имён | смысл совпадает (судья) | что было не так |
|---|---|---|---|
| свободный ответ + список цитат | 6/10 | 5/10 | модель писала примеры кода в стиле Django (`User.objects.select_related(...)`) и цитировала одну строку на пять фактов |
| утверждения, у каждого своя цитата | 9/10 | 5/10 | выдуманные примеры исчезли; оставшиеся «не подтверждено» — ошибки судьи |

По ходу исправлены ещё две вещи. Ollama по умолчанию запускает модель с окном 4096 токенов, и промпт
с пятью кусками кода обрезался — один прогон завис до таймаута; теперь окно 16384. Кроме того, сверка цитат
не учитывает переносы строк: модель часто склеивает многострочный докстринг в одну строку.

# Поиск (день 23): реранкинг, фильтр релевантности и переписывание запроса

К семантическому поиску по коду из дня 22 (эмбеддинги Ollama в FAISS) добавлены этапы до и после векторного поиска:

```
запрос ──► [rewrite: LLM] ──► векторный поиск, fetch_k на запрос ──► [фильтр: min_score] ──► [rerank] ──► top k
           исходный + переписанный                                    косинусная близость    heuristic | llm
```

| Этап | Опция | Что делает |
|---|---|---|
| Переписывание запроса | `--rewrite` | LLM переводит вопрос на английский и добавляет вероятные имена функций и классов. Кандидаты по исходному и переписанному запросам объединяются, у каждого чанка остаётся лучший из двух скоров. |
| Топ-K до фильтрации | `--fetch-k N` | Сколько кандидатов на запрос попадает во второй этап (по умолчанию `k`). |
| Порог | `--min-score X` | Отбрасывает кандидатов с косинусной близостью ниже `X`. |
| Эвристический реранкер | `--rerank heuristic` | Близость плюс бонус за слова запроса (идентификаторы делятся по snake_case и CamelCase) в имени и коде чанка. |
| LLM-реранкер | `--rerank llm` | Отдельная модель оценивает каждого кандидата от 0 до 10. Кандидаты с оценкой ниже `--min-relevance` (по умолчанию 5) отбрасываются. |
| Топ-K после фильтрации | `-k N` | Сколько результатов вернуть. Если вернулось меньше или ничего, остальные недостаточно релевантны. |

LLM задаётся опцией `--llm` (по умолчанию `qwen2.5-coder:3b`) и работает через Ollama с temperature 0.

## Поиск


## Сравнение режимов

В `eval/ormar.json` 19 вопросов по ORM ormar, у каждого перечислены qualified names правильных ответов:
11 вопросов на английском, 4 на русском и 4, на которые в коде ответа нет (пустой `relevant`).
Для последних правильный результат — пустой ответ.

```sh
python -m codeindex eval eval/ormar.json -v      # все 8 режимов
python -m codeindex eval eval/ormar.json --modes baseline filter --min-score 0.65
```

Метрики:
- **hit@k** — доля вопросов с ответом, у которых правильный результат попал в топ-k;
- **MRR** — среднее 1/ранг первого правильного результата;
- **precision** — доля правильных среди возвращённых результатов;
- **rejected** — доля вопросов без ответа, на которые вернулся пустой список;
- **avg results** — сколько результатов в среднем возвращается;
- **sec/query** — время на запрос.

### Результаты (k=5, min score 0.62, fetch k 20, min relevance 5)

| режим | hit@k | MRR | precision | rejected | avg results | sec/query |
|---|---|---|---|---|---|---|
| baseline (без фильтра и rewrite) | 0.47 | 0.39 | 0.21 | 0.00 | 5.00 | 0.02 |
| filter | 0.47 | 0.39 | 0.25 | 0.75 | 2.53 | 0.02 |
| heuristic | 0.53 | 0.39 | 0.25 | 0.75 | 2.53 | 0.02 |
| llm | 0.53 | 0.44 | 0.25 | 0.75 | 2.53 | 6.83 |
| rewrite | 0.60 | 0.47 | 0.21 | 0.00 | 5.00 | 0.48 |
| rewrite+filter | 0.60 | 0.47 | 0.21 | 0.50 | 4.05 | 0.48 |
| rewrite+heuristic | 0.73 | 0.48 | 0.27 | 0.50 | 4.05 | 0.49 |
| **rewrite+llm** | **0.73** | **0.57** | **0.27** | **0.75** | 4.00 | 8.38 |

LLM `qwen2.5-coder:3b`. Каждый режим кроме baseline и rewrite использует порог 0.62; реранкеры получают
до 20 кандидатов на запрос и возвращают 5.

Выводы:
- **Порог** не меняет, что находится, но отсекает мусор: 3 из 4 вопросов без ответа получают пустой ответ,
  а результатов в среднем вдвое меньше (2.5 вместо 5). Цена — русские вопросы без перевода тоже отсекаются.
- **Rewrite** возвращает русские вопросы: «как удалить запись из базы» находит `Model.delete`,
  «сохранить модель вместе со связанными объектами» — `Model.save_related`.
  Но переписанный мусорный запрос («pandas read_csv…») набирает больше, и порог отсекает его реже (0.50).
- **Эвристика** поднимает правильные ответы, когда слова запроса совпадают с именами (`select_related`, `order_by`).
- **LLM-реранкер** лучше всех ставит правильный ответ первым (MRR 0.57 против 0.39) и сам отбрасывает
  мусор, который прошёл порог после rewrite (rejected снова 0.75). Цена — ~8 секунд на запрос вместо 0.02.
- Размер реранкера важен: с `qwen2.5-coder:1.5b` режим `llm` хуже baseline (hit@k 0.40, MRR 0.27) —
  модель ставит 8/10 нерелевантному коду и 1/10 `QuerySet.paginate`.
- Ни один режим не находит `pre_save`, `transaction` и `prefetch_related`: их нет среди 20 ближайших кандидатов выше порога,
  а второй этап может только переставить или отбросить то, что нашёл первый.

## Настройка порога

На этом индексе релевантные чанки набирают примерно 0.62–0.78, нерелевантные 0.55–0.60
(nomic-embed-text сжимает косинусные скоры в узкую полосу), поэтому порог 0.62 стоит в зазоре.
Русские вопросы без перевода набирают около 0.53, так что порог без переписывания отсекает и их.
