# devbot — Telegram-ассистент Python-разработчика

Бот отвечает через DeepSeek, вызывает встроенные и MCP-инструменты, работает
с GitHub-репозиториями пользователя, запускает его код и сам сжимает длинную
историю. Каждому одобренному пользователю Telegram соответствует отдельный
пользователь ОС `user-<id>`, и всё, что касается его файлов, идёт от его имени.

Только Linux; бот и `admin.py` запускаются от root.

## Установка

```bash
cd final/bot
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env        # заполнить TELEGRAM_BOT_TOKEN и DEEPSEEK_API_KEY
```

Нужны системные `git`, `ssh-keygen`, `useradd`, `usermod`, `userdel`, `pkill`
и `/usr/bin/python3` (или другой путь в `SYSTEM_PYTHON`) — из него создаются venv
пользователей и запускается `tools/fs_worker.py`, поэтому он должен быть
доступен пользователям ОС (venv бота в каталоге бота им недоступен).

### `.env`

Все переменные перечислены в `.env.example`. Обязательны `TELEGRAM_BOT_TOKEN`
и `DEEPSEEK_API_KEY`; остальное — лимиты со значениями по умолчанию.
`DB_PATH` и `MCP_CONFIG_PATH` считаются относительно каталога бота.

### `mcp.json`

```json
{
  "servers": {
    "fetch": {"command": "uvx", "args": ["mcp-server-fetch"], "env": {}},
    "help":  {"url": "http://127.0.0.1:8770/mcp"}
  }
}
```

stdio-сервер — `command`/`args`/`env`, streamable HTTP — `url`. Инструменты
сервера получают префикс `<server>__`. Сервер, который не поднялся, пропускается
с записью в лог.

`help` — справка по боту (50 статей, поиск по ним и короткий ответ через
DeepSeek), инструмент `help__help`. Это отдельный сервер из `final/help/`:
установка и запуск — в [`final/help/README.md`](../help/README.md). Запускайте
его до бота: MCP-серверы подключаются только при старте. Без него бот работает
как обычно, просто без справки. Пользователь может спросить справку и сам:
`/help как подключить приватный репозиторий` — вопрос после `/help` уходит
в `help__help`, ответ видит только он (без модели и истории). Без сервера
`/help <вопрос>` отвечает, что справка недоступна, и показывает список команд.

## Запуск

```bash
sudo .venv/bin/python bot.py
```

При старте бот проверяет Linux, root и наличие утилит (иначе — сообщение в stderr
и код 1), выставляет права на свои файлы и проверяет пользователей ОС всех
одобренных пользователей (недостающих создаёт).

### Первый пользователь

1. Пользователь пишет боту `/start` — заявка в статусе `pending`.
2. Администратор:

```bash
sudo .venv/bin/python admin.py list --status pending
sudo .venv/bin/python admin.py approve <telegram_id>   # создаёт user-<id>, шлёт уведомление
sudo .venv/bin/python admin.py block <telegram_id>     # блокирует user-<id>, убивает его процессы
sudo .venv/bin/python admin.py delete <telegram_id>    # удаляет user-<id> с домашним каталогом и все данные
```

`id` пользователя ОС — внутренний `users.id`, не `telegram_id` (видно в `list`).

### SSH-ключ для GitHub

`/git ssh` создаёт ключ ed25519 в `<home>/.ssh` пользователя ОС и показывает
публичную часть. Её нужно добавить в GitHub: Settings → SSH and GPG keys, или
Deploy keys репозитория с галочкой «Allow write access». После этого
`/tasks <id>` клонирует и приватные репозитории, а `/git push` работает.
`/git ssh new` перегенерирует ключ (старый в GitHub перестанет работать).

## Команды

| команда | что делает |
|---|---|
| `/start` | заявка на доступ |
| `/tasks` | список задач; `/tasks <id>` — переключиться; `/tasks <id> <owner/name>` — создать/обновить и переключиться (рабочая копия клонируется заново) |
| `/memory [текст]` | показать или заменить память активной задачи |
| `/git` | статус; `commit [msg]`, `push`, `diff`, `reset`, `ssh [new]` |
| `/run <file.py> [args]`, `/run -m <module> [args]` | запуск в venv пользователя |
| `/pip <spec…>`, `/pip -r <file>`, `/pip` | установка пакетов / список установленных |
| `/tools` | каталог инструментов (тот же, что видит модель) |
| `/tool <name> [json]` | вызвать инструмент самому; результат только вам |
| `/agents`, `/agents_clear` | показать/удалить AGENTS.md (задать — прислать файл `.md`) |
| `/context` | задача, заполнение контекста, история, сводка |
| `/summary` | краткое изложение диалога (ничего не меняет) |
| `/reset` | очистить историю чата |

Обычный текст уходит модели. История общая для всех задач пользователя;
при переключении задачи меняются только блок задачи и её память в системном промпте.

## Развёртывание: systemd

```ini
# /etc/systemd/system/devbot.service
[Unit]
Description=devbot Telegram assistant
After=network-online.target
Wants=network-online.target

[Service]
User=root
WorkingDirectory=/opt/devbot/final/bot
ExecStart=/opt/devbot/final/bot/.venv/bin/python bot.py
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now devbot
journalctl -u devbot -f
```

## Безопасность

### Как устроена изоляция

- Каждый одобренный пользователь — пользователь ОС `user-<id>` со своей группой,
  без пароля, с shell `/usr/sbin/nologin`, без дополнительных групп. Comment
  `devbot account <id>` (без двоеточия — это разделитель полей `/etc/passwd`) отличает его от чужих пользователей с тем же именем —
  такие бот не трогает.
- Домашний каталог `<home>` (`0700`) содержит `.workspace` (рабочая копия активной
  задачи), `.venv` и `.ssh`. Других пользователей туда не пускают права ОС.
- Каталог бота — `root`, `0711`: пользователи ОС могут пройти внутрь к
  `tools/fs_worker.py` (`0644`), но не могут перечислить каталог. `.env` и
  `bot.db` (с `-wal`/`-shm`) — `root`, `0600`.
- Все процессы для пользователя — git, ssh-keygen, venv, pip, файловые
  инструменты, его код — запускаются одной функцией `run_as` (`run_as.py`):
  `user=`/`group=` пользователя, `extra_groups=[]`, `umask=0o077`, новая сессия,
  `stdin` закрыт, окружение собрано с нуля (никаких переменных бота),
  `setrlimit` на CPU, память, размер файла и число процессов. По таймауту
  убивается вся группа процессов.
- Файловые инструменты выполняет `fs_worker.py` от имени пользователя; поверх
  прав ОС он проверяет пути (`resolve_path`: только относительные, без выхода
  за рабочую копию через `..` и симлинки, без `.git/`).
- Приватный SSH-ключ создаётся и читается только пользователем ОС и никуда не
  отправляется.

### Что изоляция не закрывает

- **Сеть** не ограничена: код пользователя может ходить куда угодно.
- **Общие ресурсы**: `/tmp`, `/dev/shm`, CPU, диск и память машины общие;
  `setrlimit` лишь сдерживает отдельный процесс и число процессов, но не даёт квот.
- **MCP-серверы** из `mcp.json` запускаются процессом бота, то есть от root.
  Это доверенная конфигурация администратора — подключайте только то, чему доверяете.
- Локальные уязвимости ядра/setuid-программ — вне модели угроз; для жёсткой
  изоляции нужен контейнер или VM на пользователя.

## Тесты

```bash
.venv/bin/python -m pytest
```

Обычные тесты не требуют root, сети и Telegram: `run_as` подменяется версией
с той же сигнатурой, запускающей процессы от текущего пользователя; системные
команды (`useradd` и т. п.) идут через `os_users.system`, которую тесты мокают;
GitHub заменён локальными bare-репозиториями, LLM и pip замоканы.

Интеграционные тесты `@pytest.mark.root` (реальные пользователи ОС, права,
`block`) без root пропускаются. Запуск в Docker от root — на копии бота,
чтобы тесты не меняли права в рабочем каталоге:

```bash
docker run --rm -v "$PWD":/src:ro python:3.11-bookworm bash -c '
  cp -r /src /opt/bot && cd /opt/bot &&
  pip install -q -r requirements.txt &&
  SYSTEM_PYTHON=/usr/local/bin/python python -m pytest -m root -v'
```
