# Задача: Telegram-бот — ассистент Python-разработчика

Сделай в каталоге `final/bot/` Telegram-бота, который работает как ассистент
Python-разработчика. Бот работает через LLM, умеет вызывать инструменты
(встроенные и MCP), пускает только пользователей, одобренных администратором,
и сам сжимает историю диалога, когда она становится длинной.

Бот работает на Linux с правами root: каждому одобренному пользователю
Telegram соответствует отдельный пользователь ОС, и вся работа с его файлами,
git, pip и запуск его кода идут от имени этого пользователя ОС.

## Стек

- Python 3.11+, `python-telegram-bot==21.6` (async, long polling).
- LLM: DeepSeek через `openai==1.51.2` (`base_url=https://api.deepseek.com`),
  модель и ключ берутся из `.env`.
- MCP-клиент: `mcp==2.3.0`.
- Хранилище: SQLite (`sqlite3` из стандартной библиотеки), один файл `bot.db`.
- `python-dotenv`, `jsonschema` (проверка аргументов инструментов), `pytest`.
- Только Linux. Системные `git`, `ssh-keygen`, `useradd`, `usermod`,
  `userdel`, `pkill` (вызываются через `asyncio.create_subprocess_exec` /
  `subprocess.run`, без shell; без GitPython). Смена пользователя — штатными
  параметрами `subprocess` (`user=`, `group=`, `extra_groups=[]`, `umask=`),
  без `sudo`/`su`.
- Без ORM, без веб-фреймворков, без лишних слоёв абстракции.

## Структура

Бот целиком живёт в `final/bot/` и ничего не кладёт выше: в `final/` будут
другие части проекта. Все пути (`bot.db`, `mcp.json`, `.env`, `prompts/`)
разрешаются относительно каталога бота, а не текущей директории запуска.

```
final/bot/
  bot.py            # Telegram-хендлеры, точка входа
  admin.py          # консольная утилита управления пользователями
  config.py         # загрузка .env и констант
  storage.py        # SQLite: users, tasks, messages, схема и миграция
  llm.py            # клиент DeepSeek, цикл вызова инструментов
  context.py        # сборка контекста и суммаризация
  git_ops.py        # рабочие копии, SSH-ключи, команды /git
  os_users.py       # проверка прав root, создание/блокировка/удаление пользователей ОС, права каталогов
  run_as.py         # единственная точка запуска процессов от имени пользователя ОС
  tools/
    registry.py     # единый реестр инструментов + универсальный инструмент
    builtin.py      # встроенные инструменты (PyPI, docs, время)
    files.py        # файловые инструменты: проверка аргументов, вызов fs_worker
    fs_worker.py    # исполняет файловые операции от имени пользователя ОС (только stdlib)
    runner.py       # venv пользователя, pip_install, run_python
    mcp_client.py   # подключение к MCP-серверам, адаптер в реестр
  prompts/
    system.md       # системный промпт (текст ниже)
  mcp.json          # список MCP-серверов
  .env.example
  requirements.txt
  README.md
  tests/
  .gitignore        # .env, bot.db
```

Данные пользователей лежат не в каталоге бота, а в домашнем каталоге
пользователя ОС (`<home>`, см. раздел 1):

```
<home>/             # /home/user-<id>, владелец user-<id>, 0700
  .workspace/       # рабочая копия репозитория активной задачи
  .venv/            # venv пользователя
  .ssh/             # id_ed25519{,.pub}, known_hosts
```

## 1. Пользователи и доступ

Таблица `users`: `id` (INTEGER PK AUTOINCREMENT — внутренний id учётной
записи, по нему называется пользователь ОС), `telegram_id` (UNIQUE), `username`, `first_name`,
`status` (`pending` | `approved` | `blocked`), `agents_md` (TEXT, NULL),
`created_at`, `updated_at`.

- `/start` регистрирует пользователя со статусом `pending` (если его ещё нет)
  и отвечает, что заявка ждёт одобрения администратора. Повторный `/start`
  ничего не дублирует.
- Каждое входящее обновление, кроме `/start`, проверяет статус. Если статус
  не `approved` — короткий отказ, LLM не вызывается, в историю ничего не пишется.
  Проверка в одном месте (общий декоратор или фильтр), а не в каждом хендлере.

Консольная утилита `admin.py` (argparse, работает с тем же `bot.db`):

```
python admin.py list [--status pending|approved|blocked]
python admin.py approve <telegram_id>    # создаёт (или разблокирует) пользователя ОС
python admin.py block <telegram_id>      # блокирует пользователя ОС, убивает его процессы
python admin.py delete <telegram_id>     # удаляет пользователя ОС с домашним каталогом, задачи и историю
```

`list` показывает `id`, `telegram_id`, имя, статус и имя пользователя ОС.

При `approve` и `block` утилита отправляет пользователю уведомление через
Bot API (`sendMessage` по токену из `.env`). Если отправить не получилось,
статус всё равно меняется, а утилита печатает предупреждение. Несуществующий
`telegram_id` — понятная ошибка и ненулевой код выхода. `admin.py` тоже
проверяет права root при старте (кроме `list`).

### Права root и пользователи ОС

**Проверка при запуске.** `bot.py` до начала polling проверяет:
`sys.platform == "linux"`, `os.geteuid() == 0`, наличие `useradd`, `usermod`,
`userdel`, `pkill`, `git`, `ssh-keygen` (`shutil.which`). Любая проверка не
прошла — понятное сообщение в stderr и выход с кодом 1, бот не стартует.
Затем бот выставляет права на свои каталоги (см. ниже) и для каждого
`approved` пользователя проверяет, что пользователь ОС и его каталоги есть
(`ensure_os_user`; отсутствующее создаётся, с предупреждением в логе).

**Пользователь ОС** для учётной записи — `user-<id>`, где `id` — `users.id`
(не `telegram_id`). Своя группа, обычный домашний каталог, без пароля и без shell:

```
useradd --user-group --create-home --shell /usr/sbin/nologin \
        --comment "devbot account:<id>" user-<id>
```

`<home>` всегда берётся из `pwd.getpwnam("user-<id>").pw_dir` (обычно
`/home/user-<id>`), а не собирается строкой. Ни в какие дополнительные группы
(`sudo`, `docker`, …) пользователь не добавляется.

- `approve` → `ensure_os_user`: если пользователь ОС уже есть и его comment
  совпадает с маркером `devbot account:<id>` — разблокировать
  (`usermod -U`); если есть, но маркер другой — отказ (чужой пользователь
  ОС, не трогаем); если нет — создать. Затем `<home>` → `0700`, и от имени
  пользователя ОС создаются `<home>/.workspace`, `<home>/.ssh` (`0700`).
  Только после успеха всего этого статус в БД → `approved`. Ошибка
  на любом шаге — статус не меняется, ненулевой код выхода.
- `block` → `usermod -L`, `pkill -KILL -u user-<id>`, статус → `blocked`.
  Домашний каталог (рабочая копия, venv, ключ) сохраняется; повторный
  `approve` возвращает доступ.
- `delete` → `pkill -KILL -u user-<id>`, `userdel --remove user-<id>`
  (удаляет и `<home>`), затем записи в БД.

**Права** (выставляет `os_users.py`, проверяется при старте):

| путь | владелец | права |
|---|---|---|
| каталог бота | root | `0711` |
| `.env`, `bot.db` (и `-wal`/`-shm`) | root | `0600` |
| `tools/fs_worker.py` | root | `0644` |
| `<home>` пользователя ОС | `user-<id>` | `0700` |

Так пользователь ОС не может ни прочитать секреты бота и БД, ни перечислить
каталог бота, ни заглянуть в домашние каталоги других пользователей.

**Всё от имени пользователя ОС.** Любая операция с файлами пользователя и
любой процесс для него (git, ssh-keygen, venv, pip, запуск кода, файловые
инструменты) идут через одну функцию `run_as(ctx, argv, cwd, timeout, ...)`
в `run_as.py`. Она:

- запускает процесс с `user=`/`group=` пользователя ОС, `extra_groups=[]`,
  `umask=0o077`, `start_new_session=True`, `stdin=DEVNULL`, без shell;
- собирает окружение с нуля: `HOME=<home>`, `USER`, `LOGNAME`, `PATH`, `LANG` и
  переданные вызывающим переменные — ничего из окружения бота;
- выставляет `resource.setrlimit` в `preexec_fn`: CPU, память
  (`RUN_MEMORY_MB`), размер файла, `RLIMIT_NPROC` (теперь работает
  per-user — защищает от fork-бомбы);
- по таймауту убивает всю группу процессов и возвращает пометку «таймаут»;
- возвращает `exit_code`, `duration`, `stdout`, `stderr`.

Сам процесс бота (root) читает и пишет только свои файлы: `bot.db`, `.env`,
`prompts/`, `mcp.json`. Прямых `open()`/`Path.write_text()`/`shutil` по путям
в домашних каталогах пользователей в коде бота нет (кроме `chmod <home>` в
`ensure_os_user`; `userdel --remove` при `delete`).

## 2. AGENTS.md пользователя

У каждого пользователя может быть свой `AGENTS.md` — инструкции его проекта.

- Пользователь присылает файл документом (`AGENTS.md` или любой `.md`) —
  бот сохраняет текст в `users.agents_md`. Ограничение размера — `AGENTS_MD_MAX_CHARS`
  из конфига (по умолчанию 20 000 символов); файл больше лимита отклоняется с объяснением.
- `/agents` — показать текущий текст (или сказать, что его нет).
- `/agents_clear` — удалить.

## 3. Задачи (проекты на GitHub)

Отдельная таблица `tasks` связывает пользователя с его проектами:
`telegram_id` (FK → `users`), `task_id` (TEXT, задаёт пользователь),
`repo_url` (TEXT), `memory` (TEXT, NULL — память задачи), `created_at`,
`updated_at`; первичный ключ
`(telegram_id, task_id)`. В `users` добавляется `current_task_id` (NULL) —
активная задача.

- `task_id`: `[A-Za-z0-9_.-]{1,64}`.
- `repo`: принимается `owner/name` или `https://github.com/owner/name[.git]`,
  хранится нормализованным как `https://github.com/owner/name`. Всё остальное
  отклоняется с подсказкой формата. Существование репозитория не проверяется.

Команда `/tasks`:

- `/tasks` — список задач пользователя `id — repo`, активная помечена.
  Задач нет — подсказка, как создать.
- `/tasks <id>` — переключиться на существующую задачу; нет такой — ошибка
  со списком имеющихся id.
- `/tasks <id> <repo>` — создать задачу или обновить её репозиторий
  (upsert) и переключиться на неё.
- Больше двух аргументов — подсказка по использованию.

История чата привязана к пользователю, а не к задаче: переключение задачи
историю не меняет — меняются только строка текущей задачи и память задачи
в префиксе контекста (раздел 6). Пользователь может общаться и без
выбранной задачи.

### Память задачи — `/memory`

У каждой задачи своя память — свободный текст, который пользователь
задаёт сам (договорённости, контекст, планы по проекту).

- `/memory` — показать память активной задачи (или сказать, что она пуста).
- `/memory <text>` — заменить память активной задачи целиком на `<text>`
  (весь текст после команды, с переносами строк). Больше `MEMORY_MAX_CHARS`
  (по умолчанию 4000) — отказ с объяснением, старая память не меняется.
- Нет активной задачи — подсказка `/tasks <id>`.

Память — часть неизменяемого префикса контекста: не суммаризируется и не
хранится в `messages`. `/reset` её не трогает. `/tasks` в списке помечает
задачи с непустой памятью.

При каждом переключении на задачу (`/tasks <id>` и `/tasks <id> <repo>`) бот
клонирует её репозиторий в `<home>/.workspace`. Перед клонированием
`<home>/.workspace` удаляется целиком и создаётся пустым — от имени
пользователя ОС (операция `reset_workspace` в `fs_worker`), затем
`git clone <url> .` тоже через `run_as`. Поэтому
у пользователя всегда одна рабочая копия — активной задачи; незакоммиченные
изменения прежней задачи при этом теряются, и ответ `/tasks` об этом
предупреждает, если в старой копии были изменения. Клонирование идёт по SSH
(`git@github.com:owner/name.git`) ключом пользователя; если ключа нет —
по HTTPS (сработает только для публичных repo), а push-URL `origin` всё равно
выставляется на SSH. Ошибка клонирования не отменяет переключение задачи:
пользователь получает текст ошибки и подсказку (`/git ssh`, повторить `/tasks <id>`).

## 4. Git

### SSH-ключ

Ключи хранятся в `<home>/.ssh/id_ed25519{,.pub}` — каталог
принадлежит пользователю ОС (`0700`), приватный ключ `0600`. Ключ создаёт и
читает только пользователь ОС через `run_as`. Приватный ключ никогда не
отправляется в Telegram, не пишется в лог и не попадает в контекст модели.

- `/git ssh` — если ключа нет, генерирует пару
  (`ssh-keygen -t ed25519 -N "" -C devbot-<telegram_id>` через `run_as`);
  публичный ключ получает через `ssh-keygen -y -f <key>` (тоже `run_as`)
  и выводит его с инструкцией: добавить его в GitHub (Settings → SSH keys или
  Deploy keys репозитория с правом записи).
- `/git ssh new` — перегенерирует пару с предупреждением, что старый ключ
  в GitHub перестанет работать.

Все git-команды запускаются через `run_as` с
`GIT_SSH_COMMAND="ssh -i <key> -o IdentitiesOnly=yes -o StrictHostKeyChecking=accept-new -o UserKnownHostsFile=<home>/.ssh/known_hosts"`
и `GIT_TERMINAL_PROMPT=0`, с таймаутом `GIT_TIMEOUT_SEC` (по умолчанию 60).

### Команда `/git`

Работает с `<home>/.workspace`. Нет активной задачи или рабочей
копии — подсказка `/tasks <id>`. Выполняется под тем же per-user локом,
что и сообщения в чат.

- `/git` — статус: ветка, ahead/behind относительно upstream, список
  изменённых/новых/удалённых файлов (`git status --porcelain=v1 --branch`).
  Нет изменений — «рабочая копия чистая».
- `/git commit [message]` — `git add -A` (учитывает `.gitignore`), затем commit.
  Нечего коммитить — так и сказать. Без `message` сообщение коммита
  генерирует модель по `git diff --cached` (обрезанному до `GIT_DIFF_MAX_CHARS`):
  одна строка до 72 символов в повелительном наклонении, при необходимости
  тело. Автор — `first_name`/`username` из Telegram и
  `<telegram_id>@users.noreply.telegram` (через `-c user.name=… -c user.email=…`).
  Ответ: короткий hash, сообщение, список файлов.
- `/git push` — `git push origin HEAD`. Без SSH-ключа — подсказка `/git ssh`.
  Никакого `--force`. Ошибку git (нет доступа, non-fast-forward) показать
  пользователю коротко и с подсказкой.
- `/git diff` — собрать `git diff HEAD` и список неотслеживаемых файлов,
  обрезать до `GIT_DIFF_MAX_CHARS`, отправить модели отдельным запросом без
  инструментов и вывести пользователю summary: что изменено по файлам,
  смысл изменений, замеченные риски (баги, забытые debug-вызовы, секреты).
  Нет изменений — сказать без вызова модели. В историю чата не пишется.
- `/git reset` — откат всех незакоммиченных изменений:
  `git reset --hard HEAD` + `git clean -fd` (игнорируемые файлы не трогаются).
  Перед выполнением — подтверждение inline-кнопкой со списком того, что будет
  потеряно; кнопка действует только для этого пользователя и этой задачи.
- Любой другой аргумент — справка по `/git`.

Аргументы пользователя никогда не попадают в shell; `message` передаётся
отдельным аргументом `git commit -m`. Вывод git обрезается под лимит Telegram.

## 5. Инструменты

### Единый реестр

Встроенные и MCP-инструменты регистрируются в одном реестре и для модели
неотличимы. У каждого инструмента: `name`, `description`, `parameters`
(JSON Schema) и async-функция вызова `(ctx, arguments) -> str`, где `ctx` —
контекст вызова: `telegram_id` и путь рабочей копии пользователя.
Встроенные инструменты берут из `ctx` пользователя; аргумент «чей это
пользователь/каталог» модели и пользователю не даётся. MCP-адаптер `ctx`
игнорирует. Имена MCP-инструментов получают префикс сервера:
`<server>__<tool>`, чтобы не было коллизий.

### Универсальный инструмент

Модели передаётся ровно один function-tool:

```json
{
  "name": "call_tool",
  "description": "Вызвать инструмент из каталога в системном сообщении.",
  "parameters": {
    "type": "object",
    "properties": {
      "name": {"type": "string"},
      "arguments": {"type": "object"}
    },
    "required": ["name", "arguments"]
  }
}
```

Сам каталог (название, описание, параметры) модель видит текстом в отдельном
системном сообщении (см. раздел 6).

### Диспетчер и источник вызова

Инструменты вызывают двое — модель и пользователь — и оба идут через один
диспетчер `call_tool(ctx, name, arguments)`, который возвращает текст результата
или текст ошибки и сам ничего никуда не отправляет:

1. ищет инструмент по `name` — нет такого → ошибка с перечнем доступных имён;
2. проверяет `arguments` по JSON Schema инструмента (`jsonschema`) — ошибка
   валидации возвращается текстом, чтобы вызывающий исправил вызов;
3. вызывает инструмент с таймаутом (`TOOL_TIMEOUT_SEC`, по умолчанию 30);
4. результат обрезает до `TOOL_RESULT_MAX_CHARS` с пометкой об обрезке.

Любая ошибка инструмента превращается в текст результата, а не роняет
обработку. Результат всегда получает тот, кто вызвал:

- **Вызов модели** (function call `call_tool`): результат уходит только
  модели — сообщением `tool` в историю чата — и пользователю не
  показывается; пользователь видит лишь финальный ответ модели (пока
  инструмент выполняется, можно показывать статус «вызываю `<name>`…»).
  Цикл «модель → инструмент → модель» ограничен `MAX_TOOL_ITERATIONS`
  (по умолчанию 8).
- **Вызов пользователя** — команда `/tool <name> [json]`, где `json` —
  объект аргументов (по умолчанию `{}`; невалидный JSON → подсказка формата).
  Результат уходит только пользователю: модель не вызывается, в историю
  и в контекст ничего не пишется, на суммаризацию это не влияет.
  Без аргументов `/tool` выводит справку и отсылает к `/tools`.

### Встроенные инструменты

Справочные инструменты (без доступа к файлам и запуска кода):

- `pypi_package_info(name)` — версия, краткое описание, требуемый Python,
  ссылки (из `https://pypi.org/pypi/<name>/json`);
- `python_docs_link(topic)` — ссылка на раздел docs.python.org для модуля/функции стандартной библиотеки;
- `current_datetime()` — текущие дата и время UTC.

### Файловые инструменты

Работают только внутри рабочей копии пользователя `<home>/.workspace`
(та же папка, куда `/tasks` клонирует репозиторий). Нет рабочей копии —
ошибка с подсказкой `/tasks <id>`.

Исполнение — от имени пользователя ОС: `files.py` проверяет аргументы по
схеме и вызывает через `run_as` `<python> -I tools/fs_worker.py`, передавая
запрос `{"op": ..., "root": ..., "args": {...}}` JSON-ом в stdin и получая
JSON-ответ из stdout. `fs_worker.py` — самостоятельный скрипт только на
stdlib, без импортов из бота и без доступа к секретам. Права ОС — основная
граница; проверка путей ниже — второй слой, чтобы давать понятные ошибки и
не трогать `.git/`.

Проверка путей — одна функция `resolve_path(root, path)` в `fs_worker.py`,
через которую проходит каждый путь:

- `path` — только относительный путь от корня рабочей копии; абсолютные пути
  отклоняются;
- путь разрешается `Path.resolve()` (с раскрытием симлинков) и должен остаться
  внутри корня (`is_relative_to`) — `..` и симлинки наружу отклоняются;
- каталог `.git/` закрыт для чтения и записи;
- ошибка песочницы — текст «путь вне рабочей копии», без раскрытия
  абсолютных путей сервера.

Инструменты:

- `list_files(path=".", glob="**/*", max_results=200)` — файлы проекта
  с размерами. Учитывает `.gitignore` (через
  `git ls-files --cached --others --exclude-standard`), `.git/` не показывает;
  при превышении лимита — пометка «показано N из M».
- `read_file(path, start_line=1, end_line=null)` — содержимое с номерами строк.
  UTF-8; бинарные файлы отклоняются; больше `FILE_READ_MAX_CHARS` — обрезка
  с подсказкой, какой диапазон строк запросить дальше.
- `search_files(query, regex=false, glob="**/*", case_sensitive=false, max_results=100)`
  — поиск по всем текстовым файлам проекта (с учётом `.gitignore`):
  результаты `path:line: строка`, сгруппированные по файлам, с итоговым
  числом совпадений. Невалидный regex — понятная ошибка.
- `python_outline(path)` — структура Python-файла через `ast`: импорты,
  классы, методы, функции с номерами строк, сигнатурами и первой строкой
  docstring; синтаксическая ошибка — её текст и строка. Помогает анализировать
  проект, не читая файлы целиком.
- `write_file(path, content)` — создать файл или полностью перезаписать;
  создаёт недостающие каталоги; размер ≤ `FILE_WRITE_MAX_BYTES`.
  Ответ: «создан»/«перезаписан», число строк.
- `edit_file(path, old_str, new_str)` — точечная правка: `old_str` должен
  встречаться в файле ровно один раз, иначе ошибка (не найден / найдено N
  раз — уточни контекст). Ответ: изменённый фрагмент с номерами строк.

Запись атомарная (временный файл в том же каталоге + `os.replace`), окончание
строк и кодировка файла сохраняются. Удаления файлов нет. Инструменты
выполняются под per-user локом, поэтому не пересекаются с `/git` и `/tasks`
(переключение задачи пересоздаёт рабочую копию). Изменения файлов видны
в `/git` и откатываются `/git reset`.

### venv, установка пакетов и запуск

У каждого пользователя свой venv: `<home>/.venv` —
**вне** рабочей копии, чтобы он не удалялся при переключении задачи и не
попадал в `git add -A`. Создаётся лениво при первом обращении
(`<системный python3> -m venv` через `run_as`, т.е. файлы venv принадлежат
пользователю ОС), сразу с обновлённым `pip`.

Инструменты (как и все остальные — доступны и модели, и пользователю через
`/tool`; ответ получает источник вызова):

- `pip_install(packages=[], requirements=null)` — установить пакеты в venv
  пользователя. `packages` — список спецификаций вида `name`, `name[extra]`,
  `name==1.2`, `name>=1,<2`; каждая проверяется регуляркой, всё, что
  начинается с `-` или похоже на путь/URL (`--index-url`, `-e`, `../x`,
  `git+…`), отклоняется. `requirements` — путь к файлу в рабочей копии
  (через `resolve_path`), передаётся как `-r`. Нужно указать хотя бы одно из двух.
  Таймаут `PIP_TIMEOUT_SEC` (по умолчанию 300).
- `pip_list()` — установленные пакеты (`pip list --format=freeze`).
- `run_python(target, args=[], module=false)` — запуск наработок:
  `<venv>/bin/python <target> <args…>` или с `module=true` —
  `<venv>/bin/python -m <target> <args…>` (так запускаются `pytest`,
  `mypy`, `ruff` и CLI установленных пакетов). Скрипт `target` проходит
  через `resolve_path`; имя модуля — `[A-Za-z_][A-Za-z0-9_.]*`. `cwd` —
  корень рабочей копии; нужна активная задача с рабочей копией.

pip и запуск идут через `run_as` (от имени пользователя ОС, с его лимитами
и чистым окружением) с дополнительными переменными: `PATH` с `<venv>/bin`
первым, `VIRTUAL_ENV`, `PYTHONUNBUFFERED=1`, `PIP_DISABLE_PIP_VERSION_CHECK=1`.
Таймаут запуска — `RUN_TIMEOUT_SEC` (по умолчанию 60). Одновременно у
пользователя выполняется не больше одного процесса (per-user лок); пока он
идёт, бот показывает «выполняется…».

Результат запуска — код выхода, длительность, `stdout` и `stderr` отдельно.
Каждый поток, если длиннее `RUN_OUTPUT_MAX_CHARS`, обрезается с сохранением
начала и конца и пометкой, сколько вырезано.

- **Источник — пользователь:** отдельные сообщения: заголовок
  (команда, код выхода, время), затем `stdout` и `stderr` — каждый своим
  сообщением в блоке кода (пустой поток не отправляется). Если поток не влез
  в лимит — полная версия дополнительно приходит файлом `stdout.txt` /
  `stderr.txt`.
- **Источник — модель:** один текстовый результат инструмента с разделами
  `exit_code`, `duration`, `stdout`, `stderr` (обрезанными); пользователю
  его не показывают, модель сама пересказывает, что получилось.

Короткие команды пользователя — то же самое, что `/tool`, только удобнее:

- `/pip <spec> [<spec> …]` → `pip_install(packages=[…])`;
  `/pip -r <path>` → `pip_install(requirements=path)`; `/pip` → `pip_list()`.
- `/run <file.py> [args…]` → `run_python(target, args)`;
  `/run -m <module> [args…]` → `run_python(module=true)`.
  Аргументы разбираются `shlex.split` и передаются списком, не в shell.

**Изоляция.** Код пользователя работает от его пользователя ОС и правами
ОС отрезан от `.env`, `bot.db` и чужих каталогов (см. раздел 1). Что
остаётся открытым и должно быть описано в README: доступ в сеть не
ограничен; общие `/tmp` и системные ресурсы (лимиты `setrlimit` их лишь
сдерживают); MCP-серверы из `mcp.json` запускаются процессом бота, т.е. от
root, — это доверенная конфигурация администратора.

### MCP

`mcp.json` описывает серверы (stdio: `command`/`args`/`env`; streamable HTTP: `url`).
При старте бот подключается ко всем серверам, получает `list_tools` и
регистрирует их в реестре. Сервер, который не поднялся, логируется и
пропускается — бот работает без него. Сессии MCP закрываются при остановке бота.
`/tools` показывает пользователю список доступных инструментов
(название, описание, параметры) — тот же каталог, что видит модель.

## 6. Контекст запроса к модели

Порядок сообщений строго такой:

1. `system` — системный промпт из `prompts/system.md`; если выбрана задача,
   в конец добавляется блок «Текущая задача: `<id>`, репозиторий: `<repo_url>`»
   и, если память задачи не пуста, «Память задачи:» с её текстом;
2. `system` — содержимое `AGENTS.md` пользователя (только если есть), с заголовком
   «Инструкции проекта пользователя (AGENTS.md)»;
3. `system` — каталог инструментов: для каждого — название, описание, параметры
   (JSON Schema), плюс правило «вызывай через `call_tool`»;
4. история чата пользователя (общая для всех его задач): сначала сводка (если есть), затем сообщения
   `user` / `assistant` / `tool` в хронологическом порядке.

Части 1–3 — неизменяемый префикс: он собирается заново на каждый запрос,
никогда не попадает в суммаризацию и не хранится в таблице сообщений.

Таблица `messages`: `id`, `telegram_id`, `role`
(`user` | `assistant` | `tool` | `summary`), `content`, `tool_calls` (JSON, NULL),
`tool_call_id` (NULL), `created_at`. Вызовы инструментов и их результаты
хранятся в истории так же, как обычные сообщения.

`/reset` очищает историю чата пользователя (AGENTS.md, задачи и их память
не трогает).
`/context` показывает: активную задачу и репозиторий, есть ли память задачи,
токенов в последнем запросе, лимит, процент заполнения, число сообщений в
истории, есть ли сводка. Счётчик токенов последнего запроса хранится на
пользователя.

`/summary` — summary текущего диалога по запросу пользователя. Отдельный
запрос к модели **без инструментов** (параметр `tools` не передаётся) из:

1. части 1 контекста — системный промпт (с блоком задачи и памятью, если есть);
2. части 2 — AGENTS.md (если есть);
3. истории чата пользователя (сводка, если есть, и сообщения) **без
   инструментов**: каталог инструментов (часть 3) не передаётся, сообщения
   `tool` выбрасываются, у `assistant` убираются `tool_calls`, а сообщения
   `assistant` без текста (только вызов инструмента) выбрасываются целиком;
4. последнего `user`-сообщения с заданием: кратко изложить цель диалога,
   что сделано и решено, ключевые файлы/код/команды, открытые вопросы и
   следующие шаги.

Ответ отправляется пользователю (с разбиением на части, как обычный ответ).
`/summary` ничего не меняет: не пишет в `messages`, не трогает сводку
суммаризации и счётчик токенов. История пуста — сказать об этом без вызова
модели.

## 7. Суммаризация истории

- Всё ниже действует в пределах истории одного пользователя.
- `CONTEXT_LIMIT_TOKENS` — лимит контекста модели (в конфиге).
- После каждого ответа модели берётся `usage.prompt_tokens` последнего запроса
  (плюс токены ответа). Если сумма ≥ 60 % лимита — запускается суммаризация
  перед следующим ходом пользователя.
- Сжимаются 2/3 самых старых сообщений истории чата (части 4). Существующая
  сводка считается самым старым сообщением и входит в эти 2/3, так что старая
  сводка поглощается новой. Оставшаяся 1/3 сообщений не меняется.
- Граница не должна разрывать группу «assistant с `tool_calls` → его `tool`-ответы»:
  если граница попадает внутрь группы, сдвигай её так, чтобы вся группа
  целиком ушла в сводку.
- Сводку делает та же модель отдельным запросом без инструментов, с промптом:
  сохранить цели пользователя, принятые решения, имена файлов/функций/пакетов,
  версии, нерешённые вопросы, ключевые фрагменты кода; писать кратко.
- Результат записывается одной строкой с ролью `summary` и в контексте
  передаётся как `system`-сообщение «Сводка предыдущей части диалога: …»
  перед оставшимися сообщениями.
- В одной транзакции: вставить новую сводку, удалить все сообщения и старую
  сводку, которые в неё вошли. В базе остаётся ровно текущий контекст:
  одна сводка + несжатые сообщения.
- Если запрос на суммаризацию упал — история не меняется, ошибка логируется,
  пользователь получает ответ как обычно.

## 8. Поведение бота

- Пока модель думает — `typing`-индикатор.
- Ответы длиннее 4096 символов режутся на части по границам строк, не разрывая
  блоки кода ```` ``` ````; форматирование — `MarkdownV2` или `HTML` с
  экранированием, при ошибке разметки — повтор отправки plain text.
- Сообщения одного пользователя обрабатываются последовательно
  (`asyncio.Lock` на `telegram_id`), разные пользователи — параллельно.
- Ошибка LLM/сети → короткое сообщение пользователю, подробности в лог;
  сообщение пользователя в истории остаётся.
- Секреты только в `.env`; `.env.example` перечисляет все переменные:
  `TELEGRAM_BOT_TOKEN`, `DEEPSEEK_API_KEY`, `DEEPSEEK_MODEL`,
  `CONTEXT_LIMIT_TOKENS`, `DB_PATH`, `MCP_CONFIG_PATH`, остальные лимиты.

## 10. Тесты (pytest, без сети и Telegram)

Обычные тесты запускаются без root. Для этого `run_as` подменяется фикстурой
с той же сигнатурой, которая запускает процесс от текущего пользователя
(`user=`/`group=` не передаются), а все вызовы `useradd`/`usermod`/`userdel`/
`pkill`/`chown` идут через одну функцию в `os_users.py`, которую тесты
мокают и проверяют её аргументы.

- Права и пользователи ОС: бот не стартует при `geteuid() != 0`, не на Linux
  и без нужных утилит (код выхода 1, понятное сообщение); `approve` вызывает
  `useradd` с ожидаемыми аргументами и только потом меняет статус; ошибка
  `useradd` оставляет `pending`; существующий пользователь ОС с чужим comment
  → отказ; `block` → `usermod -L` + `pkill`; `delete` → `pkill` + `userdel`
  и удаление каталогов; `run_as` передаёт в `subprocess` uid/gid нужного
  пользователя, `extra_groups=[]`, `umask=0o077` и окружение без переменных бота.
- Интеграционные (`@pytest.mark.root`, пропускаются без root; запуск — в
  Docker-контейнере от root, команда в README): после `approve` двух
  пользователей код пользователя A через `run_python` не может прочитать
  `.env`, `bot.db`, `<home B>/.workspace`, `<home B>/.ssh` и получить список
  файлов каталога бота; файлы, созданные `write_file`, `git clone`, `pip_install`,
  принадлежат `user-<A>`; после `block` процессы пользователя убиты.

- Git (с локальным bare-репозиторием как `origin` вместо GitHub, без сети;
  URL клонирования строится одной функцией, которую тесты подменяют):
  переключение задачи пересоздаёт `<home>/.workspace`; `/git` на чистой
  и изменённой копии; `commit` уважает `.gitignore` и не падает, когда нечего
  коммитить; `commit` без сообщения берёт его из LLM (замокать); `push`
  доходит до bare-репо; `diff` без изменений не зовёт LLM; `reset` без
  подтверждения ничего не меняет, с подтверждением — откатывает изменения и
  удаляет неотслеживаемые файлы, но не игнорируемые; `/git ssh` создаёт ключ
  с правами `0600` и не пересоздаёт его без `new`.
- Регистрация: `/start` создаёт `pending`, повтор не дублирует; не-`approved`
  пользователь не доходит до LLM.
- `admin.py`: approve/block/delete меняют БД; несуществующий id → код выхода ≠ 0
  (отправку в Bot API замокать).
- Реестр: неизвестное имя, невалидные аргументы, таймаут, исключение инструмента
  → текстовая ошибка; MCP-инструмент регистрируется с префиксом
  (MCP-сессию замокать).
- Файловые инструменты (на `tmp_path`, `fs_worker` вызывается через
  подменённый `run_as`): `../x`, абсолютный путь, симлинк
  наружу и `.git/config` отклоняются; пользователь A не видит файлы
  пользователя B; `list_files` и `search_files` учитывают `.gitignore`;
  `read_file` с диапазоном и обрезкой, бинарный файл отклоняется;
  `edit_file` при 0 и при 2+ совпадениях не меняет файл; `write_file` создаёт
  каталоги и соблюдает лимит; `python_outline` на корректном и сломанном файле.
- venv и запуск: venv создаётся в `<home>/.venv` и переживает
  переключение задачи; `pip_install` отклоняет `--index-url`, `-e`, пути и
  URL (сам pip замокать); `run_python` возвращает stdout, stderr и код выхода
  раздельно; скрипт вне рабочей копии отклоняется; бесконечный цикл
  убивается по таймауту вместе с дочерними процессами; в окружении процесса
  нет `TELEGRAM_BOT_TOKEN`/`DEEPSEEK_API_KEY`; длинный вывод обрезается
  с сохранением начала и конца; `/run` и `/pip` вызывают те же инструменты,
  что `/tool`.
- Источник вызова: результат вызова модели попадает в историю как `tool` и не
  отправляется пользователю; `/tool <name> <json>` отвечает пользователю,
  не вызывает LLM и не меняет историю; невалидный JSON → подсказка.
- `/tasks`: пустой список; создание; обновление repo у существующего id
  (без дубля); переключение на существующую и ошибка для несуществующей;
  нормализация `owner/name` и URL с `.git`; невалидные id/repo отклоняются;
  задачи одного пользователя не видны другому.
- Контекст: порядок частей 1–4; без AGENTS.md часть 2 отсутствует; блок
  текущей задачи есть только при выбранной задаче, память — только если не
  пуста; после переключения задачи история та же, а блок задачи и память —
  новой задачи.
- `/summary`: запрос к LLM (замокать) содержит системный промпт, AGENTS.md
  и историю, но не содержит каталога инструментов, `tools`, сообщений `tool`
  и `tool_calls`; история и счётчик токенов после вызова не изменились;
  пустая история — без вызова LLM.
- `/memory`: показ пустой и заполненной; замена целиком; память у каждой
  задачи своя; без активной задачи — подсказка; превышение лимита не меняет
  старую память; `/reset` и суммаризация память не трогают.
- Суммаризация: при < 60 % не срабатывает; при ≥ 60 % сжимаются ровно 2/3
  самых старых, 1/3 нетронута; старая сводка поглощается; группа tool-вызова
  не разрывается; префикс (system, AGENTS.md, каталог) не меняется;
  в БД после сжатия — одна сводка + оставшиеся сообщения; при ошибке LLM
  история не меняется. LLM замокать.

## 11. README

Как установить, заполнить `.env` и `mcp.json`, запустить бота, одобрить первого
пользователя через `admin.py`, настроить SSH-ключ через `/git ssh`,
список команд бота. Развёртывание: только Linux, бот и `admin.py` запускаются
от root; пример unit-файла systemd. Отдельный раздел «Безопасность»: как
устроена изоляция через пользователей ОС `user-<id>` и права каталогов, что
она не закрывает (сеть, `/tmp`, MCP от root) и как запустить интеграционные
тесты в Docker.

## Критерии готовности

- `pytest` проходит; тесты `@pytest.mark.root` проходят в Docker от root.
- Запущенный не от root бот сразу завершается с понятной ошибкой.
- Бот запускается, новый пользователь получает «ждите одобрения»,
  после `python admin.py approve <id>` — в системе появляется `user-<id>` (по `users.id`) с домашним каталогом,
  пользователь получает уведомление и может общаться.
- `/run` скрипта, который печатает `os.getuid()` и пытается открыть `.env`,
  показывает uid `user-<id>` и `PermissionError`.
- `/tasks a owner/repo`, `/memory используем FastAPI`, затем
  `/tasks b owner/other` — диалог продолжается с той же историей, но модель
  уже не видит память задачи `a`; `/tasks a` — память `a` снова в контексте.
- `/git ssh` → ключ добавлен в GitHub → `/tasks a owner/repo` клонирует
  приватный репозиторий; после правки файла `/git`, `/git diff`,
  `/git commit`, `/git push` доходят до GitHub; `/git reset` откатывает правку.
- Модель вызывает встроенный и MCP-инструмент через `call_tool`;
  пользователь вызывает их же через `/tool` и получает результат сам.
- На запрос «найди, где используется X, и переименуй в Y» модель сама находит
  файлы через `search_files`, правит их `edit_file`, а `/git diff` показывает
  ровно эти изменения.
- `/pip requests` ставит пакет; `/run main.py` выводит stdout и stderr
  отдельными сообщениями; `/run -m pytest` запускает тесты проекта;
  на «напиши функцию и тест к ней» модель создаёт файлы, запускает pytest и
  сообщает результат.
- При длинном диалоге `/context` показывает, что после суммаризации заполнение
  упало, а в истории появилась сводка.
